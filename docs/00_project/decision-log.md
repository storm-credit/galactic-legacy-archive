## D-20260803-01 — Design before manuscript

Status: ACCEPTED
Date: 2026-08-03

### Context

## D-20260803-02 — Protagonist identity

Status: ACCEPTED
Date: 2026-08-03
Decision Owner: User + A00

### Context

에이스 조종사는 초반 직접 전투와 기체 수집에 강하고, 제독은 장기 정치·함대·세력 운영 서사를 끌기 좋다.

### Decision

주인공은 전생에 에이스 출신 최후의 패전 제독이며, 회귀 후 17세 전후의 교도군사학교 죄수 생도로 다시 시작한다. 초반에는 직접 출격하는 에이스, 중후반에는 전대장·함장·제독으로 책임 범위를 넓힌다.

전생 패전은 단순 배신이 아니라 다음 네 원인이 겹친 결과로 고정한다.

1. 전술적 승리 뒤 제도와 통치 구조를 남기지 못함.
2. 뛰어난 영웅을 자기 지휘망에 집중해 후계 조직을 약화.
3. 수도 함대를 구하려 전략 노드와 피난선단을 포기한 `오르페우스 선택`.
4. 승자 기록과 유산록 원형이 편집한 정보를 최종 결전에서 신뢰.

### Reasons

- 초반 흡입력과 후반 확장성을 함께 확보한다.
- 영웅·기체·무기 수집을 주인공이 직접 경험한다.
- 전생의 실패가 ‘더 강해지기’가 아니라 ‘사람과 제도를 다르게 대하기’라는 현생 성장으로 연결된다.

### Consequences

- 주인공은 군사·조종에 강하지만 정치·과학·정비·외교를 독점하지 않는다.
- 직접 출격은 지휘 공백과 책임 비용을 만든다.
- 미래 인물을 전력으로만 계산하는 버릇이 핵심 내적 결함이 된다.

### Affected Documents

- [[canon-core-packet-v1]]
- 향후 character bible
- 향후 macroplot

## D-20260803-05 — One-time regression and historical inertia

Date: 2026-08-03
Decision Owner: User + T06 + A00

### Context

반복 타임루프는 죽음과 손실의 무게를 약화하고, 장기적으로 시행착오 최적화가 정치·수집·함대전보다 강해질 위험이 있다.

### Options Considered

- 반복 사망 회귀
- 다중 분기 세계선
- 단일 세계선 덮어쓰기
- 역사 관성형 단일 세계선
- 미래 기록 주입형

### Decision

주인공의 회귀는 단 한 번이다. 하나의 역사선이 이어지며 자원·계급·제도 같은 구조적 압력에는 관성이 있다. 주인공의 미래 기억은 개인 경험, 군사보고, 공식 역사, 유산록 기록이 섞인 불완전한 자료다.

B2 이상의 개입은 분기 장부에 등록하고 1차·2차·3차 영향을 추적한다. 개입할수록 관련 미래정보의 신뢰도가 하락하며 적대·제3세력도 관찰하고 학습한다.

### Consequences

- 실패와 죽음은 되돌릴 수 없다.
- 미래지식은 정답지가 아니라 검증해야 할 가설이다.
- 사건 하나를 막아도 구조적 원인이 남으면 다른 형태로 재발한다.

### Affected Documents

- [[regression-causality-harness]]
- 향후 original timeline
- 향후 divergence ledger

### Reversal Condition

반복 루프가 작품의 핵심 주제와 수집·정치 엔진을 약화하지 않는다는 별도 4안 검증을 통과할 때만 재검토한다.

## D-20260808-01 — 명시적 수치와 독자 노출 이름·호칭 기준

Status: ACCEPTED
Date: 2026-08-08
Decision Owner: Author

### Context

E1 v2 교정 과정에서 한글 수량 표현을 일괄적으로 아라비아 숫자로 바꾸면서, 실제 수치 전달이 목적이 아닌 동작·관용표현과 인물 대사까지 보고서처럼 굳는 문제가 확인됐다. 또한 전체 이름, 이름, 성, 직책의 사용 위치를 작품 전체에서 일관되게 잠글 필요가 있다.

### Options Considered

- 모든 수량 표현을 아라비아 숫자로 통일
- 소설 문장에서는 한글 숫자를 기본값으로 유지
- 실제 값이 중요한 수치만 아라비아 숫자로 표기하고 문학적 자연스러움과 인물 음성을 우선

### Decision

1. 독자가 실제 값으로 인식해야 하는 나이·기간·인원·개수·횟수·날짜·시각·거리·질량·속도·비율·기체 번호·식별번호·시스템/기록/보고서/명단 수치·전술/정비/의료상의 정확한 수량은 아라비아 숫자를 우선한다.
2. 숫자 전달이 목적이 아닌 관용표현, 동작 묘사, 거리감, 인물 말투는 기계적으로 숫자로 치환하지 않는다. 정확도가 중요하지 않으면 수량을 제거하거나 자연어로 재서술한다.
3. 독자 노출 인명은 `이름 + 성` 순서로 고정한다.
4. 첫 공식 소개·명단 호출·신원 확인·공식 기록·공로 및 책임 귀속에는 전체 이름을 쓴다.
5. 일반 서술과 일상 대화에는 정본 Everyday call인 이름을 쓴다.
6. 특별한 정본 사유 없는 성 단독 호출을 금지한다.
7. 같은 장면에서 한 인물의 이름·성·전체 이름을 이유 없이 혼용하지 않는다.
8. 직책·호칭은 인물 정본에 잠긴 형태만 사용하고, 관계 변화에 따른 호칭 변경은 장면에서 명시한다.
9. 화자가 모호한 대사에는 행동·시선·반응을 붙여 식별한다.

### Reasons

- 정확한 수치가 필요한 SF·전술·정비 장면의 명료성을 보존한다.
- 소설 문장이 보고서식 숫자 나열로 굳는 것을 막는다.
- 인명과 호칭이 독자에게 하나의 안정된 표지로 기능하게 한다.
- 공식 기록과 일상 관계의 차이를 문장 수준에서 드러낸다.

### Consequences

- E1 v2의 기계적 숫자 치환을 자연스러운 문장으로 복원한다.
- 이후 원고 감사에 숫자 자연스러움, 성 단독 호출, 인명 혼용, 화자 식별 검사를 추가한다.

### Risks

- 첫 전체 이름 노출 뒤에는 공식 호출·기록 기능이 있을 때만 전체 이름을 반복한다.

## D-20260812-01 — 기동 프레임 포트폴리오 방향 B 채택
Status: ACCEPTED
Date: 2026-08-12
Decision Owner: 작가

### Context

인물 센서스가 완료되기 전까지 기동 프레임 포트폴리오는 어떤 수치 방향도 선택하지 않은 채 `HOLD` 상태였다. 작가가 "각 에이스·등장인물·적국/아군·제3세력마다 전설급 기체가 있어야 균형이 맞지 않나, 에이스 기체가 등장인물 수만큼 있어야 한다"는 방향을 제기했다.

묵향 타이탄 구조, 건담 프랜차이즈의 에이스 경제, 현 설계 정합, 한국 웹소설 리텐션 네 관점을 각각 조사한 결과 네 관점이 모두 "인물 수만큼 전설기"에 반대했다. 참고작의 실제 구조는 전설급을 한 자릿수로 잠그고, 에이스 대다수를 같은 계보 기체의 커스텀 분화로 표현하며, 네임드 인물 수가 고유 선체 수를 3~10배 상회한다. 네임드 전원에게 고유기를 준 사례들은 양산기가 무의미해지고 각성·출력 인플레로만 위기를 만드는 나선에 빠졌다 — CLAUDE.md §7 중지 조건과 동일한 병증이다.

동시에 저장소 전수 센서스가 완료되어 인물 197명(주인공 1 / 핵심 아군 4 / 적수·라이벌 9 / 반복 조연 40 / 중요 단역 143)이 확정되면서, 방향 선택의 선행 조건이 해소되었다.

### Options Considered

- **A 재사용 우선**: 후보 26–32, 독자명 모델 18–26. 최소 부하.
- **B 균형 분기**: 후보 32–40, 독자명 모델 22–30. 라이벌·세력 실루엣 확대.
- **C 수집 확장**: 후보 40–48, 독자명 26–36. 섀시 증명 14–22건 추가 필요.
- **D 최대 작전 지도**: 후보 44–58. 현 역할 근거가 이 수를 입증하지 못함 — HOLD.

### Decision

**B를 채택한다.** 근거는 두 가지다. 첫째, 아직 집필 전 설계 단계이므로 나중에 줄이는 것이 나중에 늘리는 것보다 싸다. 둘째, 센서스가 중요 단역 143명으로 기존 밴드(70–110)를 33명 초과해, 수요 자체가 A의 전제보다 크다는 것이 확인되었다.

A의 재사용 우선 방법론은 계수(計數) 방향이 아니라 **작업 절차로 유지한다** — 수요는 먼저 기존 호스트에 배정하고, 재사용이 증거 검사를 통과하지 못한 잔여만 섀시 증명으로 보낸다.

### Risks

- 방향 상향이 곧 기체 승인으로 오독될 수 있다.
- 독자명 모델 22–30은 1000화 기준 33~45화당 신규 1기로, 리텐션 렌즈가 제시한 40~55화 주기보다 빠르다.
- 중요 단역 초과분이 섀시 수요로 잘못 번역되면 C·D 방향의 증거 부족을 되살린다.

### Mitigation

- 검증기가 "선택된 방향은 반드시 작가 결정 ID를 인용"하도록 강제하고, 동시에 두 방향이 선택되면 실패한다.
- 전투 장면당 기체명 4개 이하, 지속 핵심 정체성 8개 상한, 25화 블록당 신규 명명 섀시 2개 이하는 **변경하지 않는다**. 이들은 카탈로그 크기가 아니라 독자 기억 한계를 통제한다.
- 중요 단역은 지역 선체 개체·표준 장비·기록으로 표현하며, 명명 선체 수요로만 반영한다.
- 전설·에이스는 제조 클래스가 아니라 선체 개체의 이력 지위로 유지한다.

### Affected Documents

- [[role-demand-portfolio-count-audit-v1]]
- [[maneuver-frame-lineup-master-architecture-v1]]
- [[frame-formation-combat-and-collectibility-integration-audit-v1]]
- [[decision-log]]

### Reversal Condition

섀시 증명 단계에서 후보가 32건에 미달하거나, 연재 초반 독자 반응이 기체명 인지 부하 초과를 보이면 A로 되돌린다.

## D-20260816-01 — 회차 분량 하한은 사후 게이트이며 패딩을 금지한다

Status: ACCEPTED
Date: 2026-08-16
Decision Owner: 작가

### Context

GA1 E21~100 초고 생산 후 C4 하한 검사를 수행하면서, 여러 회차가 공백 포함 5,500자 미만임을 확인했다. 보강 과정에서 `몇 자 부족한가`가 작업의 전면 지표가 되면, 승인 장면카드의 실제 장면을 복원하는 대신 묘사·독백·대사·UI를 늘려 숫자를 맞출 위험이 있다. 작가는 명시적으로 “그럴 거면 내용이나 장면을 더 넣어야지 억지로 묘사하면 안 된다”고 판정했다.

### Options Considered

- A. C4 부족 자수를 계산해 같은 분량만큼 문장을 보강한다 — 반려. 숫자가 집필 목표가 된다.
- B. C4 하한을 제거한다 — 반려. 최소 회차 밀도 검증 기능까지 사라진다.
- C. **장면 완전성을 먼저 감사하고 C4는 마지막 사후 게이트로만 사용한다** — 채택.

### Decision

1. 공백 포함 5,500자는 사후 QC 하한이다. 집필 목표가 아니다.
2. 원고 순서는 `승인 장면카드 완전 구현 → 구조·인과·동기 → 정본·연속성 → 문체·낭독 → 훅 → 패딩 삭제 → C4`로 고정한다.
3. `N자 부족 → N자 추가` 방식은 금지한다.
4. 추가·유지 문장은 행동·정보·관계·선택·인과·위험·비용·보상·후속 상태 중 하나 이상을 움직여야 한다.
5. `PADDING / REPEAT / EMPTY-SENSORY / LOOP-DIALOGUE / DECORATIVE-UI / SLOW-MOTION-FILL / THOUGHT-LOOP`을 문체/낭독 FAIL 태그로 사용한다.
6. 패딩 삭제 때문에 C4 하한 아래로 내려가도 삭제를 되돌리지 않는다. 장면카드에서 생략·압축된 승인 비트를 실제 장면으로 복원한다.
7. 승인 비트가 충분한데도 미달이면 `STRUCTURAL LENGTH REVIEW`로 보내며, 새 사건·능력·기술·죽음·관계·권한·정본 사실을 분량용으로 만들지 않는다.
8. 상한은 없다. 장면 완결이 분량보다 우선한다.

### Reasons

- D-20260812-02가 이미 “숫자가 남아 있으면 후속 에이전트가 목표로 읽는다”는 실패를 확인했다.
- 웹소설 분량은 사건·선택·저항·후속비용의 실제 장면화 결과여야 한다.
- 기능 없는 문장은 낭독에서도 정보·감정의 전진 없이 호흡만 늘린다.

### Consequences

- E21~100 보강은 C4 부족 자수 순으로 문장을 채우는 작업이 아니라, 승인 카드 대비 장면 압축·누락 및 패딩을 먼저 감사하는 작업으로 전환한다.
- 이미 보강된 E21~40도 같은 기준으로 역감사한다.
- C4는 계속 유지하되 마지막 단계에서만 사용한다.

## D-20260816-02 — 완료 작업은 검증 후 main까지 통합한다

Status: ACCEPTED
Date: 2026-08-16
Decision Owner: 작가

### Context

기존 운영은 설계·QC 작업과 원고 작업 모두 브랜치/PR에 남겨 두는 경우가 있었고, 특히 원고 PR은 작가의 별도 병합 지시를 매번 기다렸다. 작가는 “할 때마다 메인에 푸쉬까지 해줘, 앞으로는”이라고 상시 운영 지시를 내렸다.

### Options Considered

- A. 기존처럼 매 작업마다 별도 병합 승인을 다시 요청한다 — 작가의 자동 진행 지시와 충돌.
- B. 검증 없이 직접 main에 커밋한다 — 비교·CI·PR 기록이 사라져 안전하지 않다.
- C. **latest main에서 브랜치 → 검증 → PR → main 병합 → 병합 상태 재확인**을 기본 완료 흐름으로 한다 — 채택.

### Decision

1. 완료된 저장소 작업은 검증 후 PR을 거쳐 main까지 병합하는 것을 기본값으로 한다.
2. 작가가 특정 작업에 `병합하지 마`, `Draft PR로만`, `보류`라고 지시하면 그 현재 지시가 우선한다.
3. main 병합은 저장소 통합 승인이다. **콘텐츠의 `AUTHOR-APPROVED` 승격, 공개·출판·유료연재 승인을 의미하지 않는다.**
4. 원고가 main에 병합되어도 별도 콘텐츠 승인 없이는 `Status: DRAFT | REVISED`, `Publication: NOT AUTHORIZED`를 유지한다.
5. 병합 후 PR을 다시 조회해 `state=closed`, `merged=true`, 실제 merge SHA를 확인한다.

### Reasons

- 새 채팅에서도 main이 실제 작업 결과를 보유해야 중복 작업과 상태 착오가 줄어든다.
- PR 기록과 검증은 유지하면서 사용자의 자동 진행 요구를 충족할 수 있다.
- 저장소 통합과 출판/정본 승격을 분리하면 안전 게이트를 유지할 수 있다.

### Consequences

- 향후 작업 완료 보고는 브랜치/PR만이 아니라 실제 main 반영 SHA까지 포함한다.
- 기존 open manuscript PR은 이 결정만으로 즉시 일괄 병합하지 않는다. 각 배치가 현재 작업에서 검증·완료될 때 이 기본 흐름을 적용한다.
- issue #26 출판 전 하드 블로커와 `Publication: NOT AUTHORIZED`는 유지된다.

### Affected Documents

- [[CLAUDE]] §21
- [[manuscript-production-workflow-v1]] §3.9~3.10
- [[decision-log]]
- 향후 모든 GitHub 작업 흐름

### Reversal Condition

작가가 특정 작업 또는 프로젝트 전체에 대해 main 자동 병합을 중단하라고 지시할 때 재검토한다.

## D-20260814-06 — 세력 43행의 이름을 한국어로 확정

**원안**: 등록부 `블록` 열의 영어 작업명(`Education`, `Continuity Authentication Directorate`)이 하중 CSV의 `name`으로 들어가 작업지시서와 카탈로그에 그대로 노출됐다.

**변경안**: 37행 교정. 성격이 다른 두 문제였다.

1. **하위 블록 24행 — 버그.** 등록부 `역할` 열에 `교육·평가`, `운용·출동`, `왕조`, `숙청`이 처음부터 있었다. CSV를 만들 때 옆 열을 집었다. 새 명명이 아니라 원래 정본으로 되돌린 것이다. `보안`이 두 생태계에 중복되어 `학원 보안` / `항로연합 중립 무장`으로 한정했다.
2. **REC-F·AR-F 13행 — 실제로 이름이 없었다.** 한국어 이름을 새로 만들었고, 기존 한국어 행(`교도군사학원 운영 주체`, `제국 정보·계승 관리`)과 같은 서술형 기관명 방식을 따랐다. 고유명사를 지어내지 않았다. 영어 작업명은 `(작업명 ...)`으로 병기해 보존한다 — 작가가 개명하면 근거가 남는다.

**변경 이유**: CLAUDE.md §12는 새 이름 전에 명명 정본 두 곳을 확인하도록 요구한다. 1번은 그 확인을 안 해서 생긴 것이 아니라 정본이 이미 준 답을 못 읽은 것이고, 2번은 확인 결과 답이 없어서 만든 것이다.

**파급 범위**: [[named-faction-and-institution-registry-v1]], `anchor-fields-factions-v1.csv`, [[CATALOG]], [[episode-briefs]]. 13개 신규 이름은 작가 승인 전까지 §15-9에 따라 `PROPOSED`로 취급한다.
